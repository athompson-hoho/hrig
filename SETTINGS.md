# HRig settings

Open the gear in the activity rail, press **Ctrl+,**, choose **Settings** from Tools, or use **Open settings** in the command center. Settings is a dockable page, and can be maximized or detached like other panels.

## Design and feature plan

The design follows [VS Code's user/workspace settings](https://code.visualstudio.com/docs/configure/settings) and [theme picker](https://code.visualstudio.com/docs/configure/themes), plus [Orca's grouped settings reference](https://www.onorca.dev/docs/settings). The controls use HRig's compact tool-panel styling.

| Idea | Delivered behavior |
| --- | --- |
| Searchable preferences | Search setting names, descriptions, keys, and categories; filter to modified values. |
| User and project scope | Local project overrides keyed by connection and project folder; reset rows to inherit. |
| Coordinated themes | HRig Dark, Graphite, Midnight, Daylight, High Contrast, and Follow Windows across app, editor, terminal and detached panels. |
| Appearance controls | Four accent colors, installed UI fonts, density, status-bar visibility, reduced motion. |
| Editor preferences | Live font, indentation, whitespace, wrap, minimap, line-number and ligature options. |
| Diff and disk behavior | Inline/side-by-side diffs; optional clean-buffer reload; unsaved-buffer protection stays enabled. |
| Terminal preferences | Live font, line spacing, cursor, scrollback, independent color theme; local PowerShell or Command Prompt for new shells. |
| Workspace and rig defaults | Inventory refresh frequency, connection defaults, rig designer runtime and team size. |
| Notifications | Default-off desktop needs-input notifications, preserving earlier explicit opt-in; separate optional terminal alerts. |
| Transfer and discoverability | Validated preferences-only JSON import/export, per-row, per-category and scoped resets, a Recently changed filter, search highlighting, shortcut reference and About. |

## Scope and persistence

User preferences apply globally. Project preferences override them for the active connection/folder. They are stored locally in HRig's workspace.json, not in the project's source files, .vscode settings, or the remote host. The current project's effective appearance applies to the workspace and all its panels. Existing layouts, connections, unsaved buffers, and agent sessions are retained when changing preferences.

Settings are saved automatically through the existing atomic workspace persistence. Numeric and font inputs commit on blur or Enter; toggles and selections apply immediately. Resetting a project row removes its override and restores the user value. Resetting a user row restores the default. Reset scope asks for confirmation.

Seat sort order (`rig.seatSort`) also controls the sidebar's Sort sessions selection. An existing project override wins, including an explicit `name` overriding a user `activity` value. Changing the sidebar selection updates that project override when the project owns the key; otherwise it updates the user preference. Reset the project row to inherit the user order, or reset the user row to restore Name. The enum uses the same automatic workspace.json save/load lifecycle and validated imports as other preferences. Sorting preserves the current search/status filters and never opens, sends input to or relaunches a seat.

Changing terminal appearance updates the existing xterm view, without replacing its PTY. Selecting a different local shell affects newly created local terminals; remote sessions continue to use their existing harness. Reconnection remains bounded to six attempts and never launches agents. Decreasing scrollback can remove older visible history.

The Settings JSON view exports preferences only, including any configured default-root preference; it excludes saved connections, credentials, current project bindings, layouts and terminal output. Imports replace only the selected scope after full key/type/range validation. Before anything is applied, the JSON view checks the text and shows what would be added, changed, removed (the import replaces the selected scope) and skipped. Malformed JSON, an unreadable version, oversized files or a missing settings object block Apply. Individual unknown keys (for example from a newer or older HRig) and invalid values are skipped and listed, and the remaining valid settings can still be applied.

**Migration notes.** The file format is `{ "version": 1, "settings": { ... } }`. A file with a higher version is read as version 1 and flagged. Settings are never renamed silently: a key HRig does not know is skipped, so removed or renamed settings fall back to their defaults. Exporting always writes the current version.

Project override indicator: a setting the open project overrides can hide behind the value you see, because the value shown in the User scope is not the value in effect for that project. In the User scope a row shows a note when the open project overrides that setting: Overridden in this project: followed by the project value (a choice shows its label and a switch shows On or Off), or Also set in this project (same value) when the project sets the very value your user setting has, which it keeps if you later change your user setting. A line under the scope note counts them, for example This project overrides 5 settings; 3 differ from your user values., and its tooltip lists the keys (the first ten). The Project scope, which already marks its own rows with Project override and has Remove project override, is unchanged, and the count also shows there; its rows are the overrides, and Modified only lists the ones in the current category. The indicator reads the open project's own saved overrides and follows them as they change, so it is always about the project you have open. Nothing is saved, changed or sent by the indicator: it is display only, and saving, resetting and the scopes work as before.

Recently changed: the Recently changed box beside Modified only lists the settings you changed since HRig started, newest first, across every category; the order of this list replaces the category order, and a search or Modified only narrows it as usual. A change is setting, resetting or applying JSON; a setting changed more than once is listed once, at its latest change, and setting a row to the value it already had is not a change. The list is kept in memory only: it is not saved, not exported in the Settings JSON, and empty again after a restart, because HRig stores no change times. The User and Project scopes have their own lists, and the Project list belongs to the project you have open. The box is greyed out with a tooltip while nothing has changed in the scope you are looking at. It only filters the page: nothing is saved, changed or sent by it, and choosing a category or Settings JSON leaves it.

Reset category: the heading of a category view has a Reset button beside the setting count (Reset Editor in the User scope, Remove Editor overrides in the Project scope). It is shown only in a category view, not in a search, in Recently changed, or in Settings JSON, and greyed out when nothing in that category is changed. It asks first: the question names the settings it will change (up to eight, then how many more) and nothing is reset until you confirm. It resets only the changed settings of that category in the scope you are looking at. In the User scope it restores their defaults and the project's overrides remain. In the Project scope it removes the project's overrides in that category, and the user values apply again. The other category, the other scope and every setting that is not changed are left alone. It does the same as pressing each row's reset button, one setting at a time, so the settings it resets also appear under Recently changed. There is no undo; the Reset user settings and Reset project settings buttons next to the scope tabs work as before.

Search highlight: while you search, the words you typed are marked in the name and the description of each result row (the key line and the option names are not marked, so a row found only by its key or an option shows no mark). The words are matched as text, not as a pattern, so characters such as . * ( [ and \ mean themselves, and upper and lower case are the same. Marks are drawn as plain text in a highlight, never as markup, so a name or description cannot add anything to the page. Only the first 2000 characters of a text are searched, at most 20 marks are drawn in one text, and a search longer than 100 characters is not marked (it cannot occur in a name or description). Case is folded one character at a time, so a few rare letters, such as a Greek capital sigma at the end of a word, are found by the search but not marked. It is display only: it does not change what the search finds, and nothing is saved, changed or sent.

Shortcut overrides: `shortcuts.overrides` keeps the saved key changes as one line of text (up to 1000 characters), comma-separated `id=keys` pairs such as `workspace.reopenPanel=Ctrl+Shift+J,workspace.maximizePanel=Ctrl+Shift+Y`. It is one text setting because a setting holds a single value and the settings checks refuse braces, semicolons and angle brackets, so a JSON map cannot be stored. Press ? to open the Keyboard shortcuts sheet, search, choose Edit on a row that has the button, type the keys and choose Save; Reset puts one shortcut back and Reset all clears the setting. The app shortcut rows with Edit buttons listed in NAVIGATION.md under Shortcut overrides can be rebound; terminal and editor commands remain fixed. Use Ctrl, Cmd, Meta or Mod for the main modifier of your computer so one setting works on every platform; Control is an alias for that modifier except Control+Tab, which keeps physical Control for panel switching. Custom letter chords require Shift; unshifted Ctrl/Cmd letters belong to terminals and the editor. Supported keys are letters, numbers, Tab, Enter, Escape, Space, punctuation and F1-F12. Alt, OS-reserved keys, terminal/editor keys and clashes are refused. Keys used by terminals, the code editor or fixed app shortcuts are refused, as are known operating-system shortcuts and any chord another app shortcut already uses. The old keys of a moved shortcut are released to the focused panel. An entry written here by hand that is refused or unknown is ignored, never an error, and the sheet lists it. Empty (the default) leaves every key and label exactly as before. The text is saved with the other preferences, in the user scope or, when the project already has its own value, in the project scope, and the Settings JSON export and import carry it like any other text setting; there is no separate keymap file. Changes only which key press runs a command; nothing is sent to the shell or the seat.

Saved snippet transfer: In Saved snippets, Export snippets offers Copy JSON and Save to file. Import snippets accepts text you paste or a JSON file you choose; Check import previews accepted, duplicate and rejected snippets before Import changes the saved list. See TERMINALS.md for size limits and privacy details.

Terminal zoom: Ctrl/Cmd `+`, `-`, `0` and Ctrl+wheel change the font size of one terminal only (8-32 pt, remembered until the app restarts); `terminal.fontSize` stays the default for every terminal.

Status bar items: `appearance.statusBarHidden` lists the status bar items to hide, as ids separated by commas or spaces, for example `sessions, layout`. The ids are `accounts` (the Accounts button), `connection` (the Local workspace, WSL or SSH label), `source-control` (the Source control button), `reconnect` (the Reconnect all dropped button), `sessions` (the count of open sessions), `layout` (the Layout autosaved note) and `activity` (the Activity button). Ids are not case sensitive, a repeated id counts once, unknown ids are ignored and only the first 300 characters and 32 words are read. Empty text, the default, hides nothing, so the status bar is exactly what it was. The Reconnect all dropped button is drawn only while terminals are dropped and stays visible then unless `reconnect` is listed; hiding it does not remove the action, which stays in the command center as Terminal: Reconnect all dropped. A thin divider is drawn only between two shown items. The setting works in the user and the project scope, it is separate from `appearance.statusBar` (Show status bar), which still hides the whole bar and which focus mode still hides for the session, and a bar with every item hidden is an empty strip, so turn Show status bar off to remove the strip. The row is plain text (a setting holds one value and the settings checks refuse braces, semicolons and angle brackets, so a list or map cannot be stored), and the generic text rule applies: not empty, at most 300 characters. Display only; nothing is sent to the shell or the seat.

Window title: `appearance.windowTitleDetails` is off by default, and then every HRig window is titled `hRig`, as before. Turn it on and the main window's title becomes the active panel's name, the project folder's name and `hRig`, joined by ` - `, for example `Build logs - hrig - hRig`; a part that does not exist (no panel is open, or the project has no name) is left out. It is a display setting for the taskbar, the window switcher and the window list: HRig draws its own title bar, which does not change, and detached windows keep `hRig`. It follows the project and the tab you are in, including a panel you renamed. The page asks for the change through one narrow channel, `window:title`, that carries only the title text; the main process accepts it only from the main window, drops control, zero-width and direction characters, cuts the title to 100 characters (the panel name to 50 and the project name to 40, with an ellipsis) and always ends it with `hRig`, so a page cannot present another application's name. Only the last folder name of the project and the panel's name are used: never a file's content, a seat's output, a host name or a secret. It works in the User and Project scopes like the other Appearance settings.

Seat sound: `notifications.seatNeedsInputSound` is off by default, and then HRig makes no sound. Turn it on and HRig plays one short, soft tone when a seat newly needs input, in addition to Desktop attention notifications and independent of them: either can be on without the other. A seat needs input when the OpenRig inventory gives it the attention status, the one the sidebar shows with a seat's status dot; the inventory also gives that status to a seat whose startup failed or needs attention, so such a seat can sound too, while a session that failed while running (status failed) does not. Only a change sounds: the first list read after HRig starts, after you turn the setting on or after you switch connection is only taken in, so seats that are already waiting never sound, and a seat that stops waiting and then waits again sounds again. A window that was hidden refreshes the moment it is shown, so a seat that began waiting meanwhile sounds then. One tone covers any number of seats that change at once, and tones are at least 10 seconds apart; a seat that newly waits inside that pause sounds at the first refresh after it, if it is still waiting. A person's own seat never sounds, and no sound is made while a refresh is failing. The tone is made by the app (one sine tone of 880 Hz that lasts 0.15 seconds, at a tenth of full volume, from the Web Audio API in the HRig window), so there is no audio file and nothing is downloaded; if the system has no audio output, nothing sounds and the Activity log says so once. It sounds whether or not HRig is in front, as Desktop attention notifications do. It uses the seat list HRig already refreshes every `workspace.refreshInterval` seconds, so no extra read is made; it shows and sends no text and nothing goes to a seat or shell. It works in the User and Project scopes like the other Notifications settings.

Reopen last project: `workspace.restoreLastProject` is off by default, and then HRig starts exactly as before: launch already brings back your saved connection, folder and layouts. Turn it on and, once, after the workspace has loaded, HRig looks at your most recent project, the newest entry of the project history whether or not it is pinned. If launch already brought that project back, nothing changes. If launch brought back a different one, for example because the saved folder or connection is gone, HRig opens the most recent project through the same Open project check as a project under Continue where you left off: the folder must exist, and a failure leaves the Open a project dialog showing its message and changes nothing else. A project whose saved connection was removed or changed is skipped for the next most recent one, and a project on another SSH or WSL connection than the one launch already uses is not opened for you (the Activity log says so), so launch never reaches a host it would not reach anyway. It never starts or restarts a seat and never sends anything to a terminal. The setting is read from your user settings only; a project override has no effect, because no project is open yet when it is read. See NAVIGATION.md.

Seat badges: `appearance.seatBadges` is off by default, and then the sidebar's session list looks exactly as before. Turn it on and each session row shows, under its name, up to two small badges: the runtime and the model. `claude-code` is shown as Claude and `codex` as Codex; any other runtime is shown as the inventory gives it, cut to 16 characters; the generic `agent` runtime, which the inventory fills in when the CLI names none, and an empty model show no badge. The model is cut to 24 characters, and the tooltip of each badge keeps up to 80. The text comes from the OpenRig inventory, so it is treated as untrusted: control, zero-width and direction characters are dropped, runs of spaces are squeezed, a very long value is only read in part, and the result is drawn as plain text, never as markup. The row's own text (the rig name and the runtime) is unchanged. Display only: nothing is sent to the shell or the seat, nothing is saved, and the setting works in the User and Project scopes like the other appearance settings.

Hide stopped sessions: `workspace.hideStoppedSeats` is off by default, and then every session is listed as before. The eye button beside SESSIONS in the sidebar turns it on, and the same setting is in Settings under Workspace. While it is on, the list leaves out a session whose status is stopped or exited (the two statuses the terminal's seat activity also shows as Stopped) and a session of a rig the inventory calls archived; a failed session and one that needs input are never hidden. The count beside SESSIONS reads shown of total, for example 3 of 5, counted after the rig and the Find a session filter. When every match is hidden, the list says how many are hidden and has a Show stopped sessions button instead of the empty message, and the rig and the filter text stay as they were. Only the sidebar list changes: panels that are open, the command center, drag and drop and relaunch are as they were, and nothing is started, stopped or sent to a seat. The choice is kept in your user settings, so the button writes there and a project override has no effect.

Terminal bell: `terminal.bellStyle` chooses only what a bell does inside HRig (`none` or `visual`). A third choice, a desktop notification, is deliberately not a value of this setting because it already exists as Terminal bell alerts (`notifications.terminalBell`, which needs `notifications.desktop`); the two settings are independent and can both apply.

Host label and tint: there is no settings row for it. A label and color belong to one connection, not to a preference, so they are not in the table above, not in the user or project scopes and not in the Settings JSON export or import. Run Set host label and tint in the command center to give a connection a short label and a palette color; they are saved under `hostTints` in workspace.json, keyed by connection ID, and a connection without one is not marked at all. See TERMINALS.md for what the terminal header shows.

### Desktop needs-input notifications

Use Desktop needs-input notifications in Settings under Notifications, or Desktop notifications when a seat newly needs input in Attention center. Both use the effective `notifications.desktop` preference: a project override wins over the user value. The Attention checkbox updates the project override when that key already exists there; otherwise it updates the user value. Turning it off is reversible. Reset a project row to inherit the user value; reset the user row to restore the default `false`. When migrating a workspace without newer preferences, an earlier explicit desktop-notification opt-in is retained.

Enabling, re-enabling, changing the connection owner (including repointing the same saved connection), or recovering from unavailable inventory starts with a silent healthy baseline. Existing needs-input seats are not announced. Only a later observed transition into normalized `attention` can request a notification, deduplicated by seat identity within that owner. Repeated snapshots or name/activity/error changes while the seat stays in attention do not repeat it. A later observed departure and re-entry can notify again. Failed seats and reported errors are not needs-input events.

Disabled, missing, unverified, foreign or stale/unhealthy inventory cannot emit. Both explicit errors and quiet poll failures disarm the baseline; the next healthy current-owner snapshot silently seeds it again. A seat entering needs-input during failure or at that recovery snapshot may therefore go unannounced. There is no queued catch-up or delivery retry. This uses the existing inventory refresh cadence on the current connection; hidden-window inventory polling is suppressed. It adds no polling and promises no continuous background or fleet monitoring. See [navigation scope](NAVIGATION.md#desktop-needs-input-notifications).

HRig requests a silent notification with only the exact accepted seat name as its title, without a body or generated suffix. Invalid names or extra payload fields/arguments are refused. OS support, permissions, app identity, title truncation and delivery suppression can affect presentation; checked/On records a preference, not permission or confirmed delivery. See [notification privacy](PRIVACY.md#desktop-notifications).

Terminal bell and quiet alerts remain separate opt-ins, each defaulting to `false` and also requiring `notifications.desktop`. They retain the existing generic notification route and seat/shell-label and host metadata, without terminal text. The seat-name-only boundary above applies to needs-input seat alerts, not these terminal alerts.

Actual OS permission/display, keyboard and assistive-technology behavior, narrow/short layouts, themes/density and persistence across a real restart remain unobserved; source and inert tests do not establish those outcomes.

Terminal log saving: Save terminal log is a per-terminal action, not a setting. It asks before writing that terminal's retained scrollback to a local file chosen by you, and previews its size and line count with a warning that output can contain secrets. It never sends the text or adds it to diagnostics. Continuous Start log recording remains a separate, off-by-default action. See TERMINALS.md and PRIVACY.md.

## Follow-up ideas

Future candidates: custom VS Code/terminal theme imports, named profiles, remappable shortcuts for the fixed keys, per-language editor settings, settings-file synchronization, and signed automatic updates. These are not exposed as working controls in this release. Agent credentials, provider models, permissions, extension installation, and OpenRig policies stay under the owning harness rather than being silently changed by desktop preferences.

## Community themes (0.7.1)

Choose Catppuccin Mocha, Macchiato, Frappe or Latte, Nord, Dracula, Tokyo Night, or Gruvbox Dark under Appearance. HRig now has 13 palettes plus Follow Windows. Native syntax colors and all 16 ANSI terminal colors are included. Secondary UI text is adapted for readability while core colors retain the upstream palette. **Theme default** uses each theme's native accent; explicit mint, blue, violet, and amber overrides remain available and existing choices are retained.

Terminals can follow the app or use any bundled palette independently. Community themes work with user/project scopes, JSON transfers, detached windows, and live session-preserving changes. Themes are bundled data, with no runtime downloads or third-party extension execution. See [THEME_CREDITS.md](THEME_CREDITS.md) for pinned sources and bundled licenses.

High Contrast: its colors are measured, not only chosen by eye. A test computes the WCAG 2.x contrast ratio of the theme's own colors and of every text, border and control color the stylesheets draw in it: 4.5:1 is required for text and 3:1 for borders, controls and the focus ring. Borders that were too dim against its black background are now drawn in the theme's border color, the text is black on the selection highlight and on the hovered window close button, and no other theme changed. ANSI black in the terminal (about 1.3:1) and the terminal selection color (about 2.6:1) are under 3:1 and are left as they are; the terminal.minimumContrastRatio setting can lift terminal text. How the theme looks on a real screen is checked by hand.
